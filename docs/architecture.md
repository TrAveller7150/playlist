# 个人博客架构决策

状态：已确定，作为后续整理和重建项目的基线。

## 目标与边界

网站用于记录生活碎片和少量长文章，并展示音乐、画作和动画观看进度。视觉表现优先，但正文阅读、内容维护和部署流程必须保持简单可靠。

- 不提供评论、点赞、投稿、公开账号等访客交互功能。
- 写作采用本地 Markdown + Git，不建设 Web 管理后台。
- 动画进度和收藏数据自动同步；外部服务不可用时继续展示上一次成功数据。
- 音乐不接入第三方音乐 API，使用站主拥有的本地 MP3 文件和手写元数据。
- 第一阶段不使用 Supabase；确有跨设备私有数据或后台需求时再引入。

## 技术栈

| 范围 | 选型 | 用途 |
| --- | --- | --- |
| Web 框架 | Astro 5 + TypeScript | 静态页面、路由、内容集合和少量服务端能力 |
| 内容 | Astro Content Collections + Markdown/MDX | 碎碎念和长文章，使用 schema 校验 frontmatter |
| 动态交互 | 原生 TypeScript + Astro Client Islands | 动态封面、播放器和确有必要的局部交互 |
| 样式 | 原生 CSS | 延续当前视觉语言，避免额外 UI 框架 |
| 部署 | EdgeOne Pages | Git 推送后自动构建和部署 |
| 数据库 | 暂不使用 | 当前没有需要常驻数据库的功能 |
| 自动同步 | Node.js/TypeScript 构建脚本 | 拉取、规范化并缓存收藏数据 |
| 本地写作 | Obsidian 或 Typora | 以富文本/实时预览方式直接编辑 Markdown |

不采用完整 SPA。Astro 默认输出静态 HTML，只对动态封面和音乐播放器加载客户端 JavaScript，以控制首屏负担。

## 内容模型

建议迁移后的核心目录如下：

```text
src/
  components/             通用展示组件
  content/
    notes/                碎碎念，Markdown
    articles/             长文章，Markdown 或 MDX
    config.ts             内容 schema
  data/
    collections/          手写收藏元数据
    generated/            自动同步并提交的缓存数据
  features/
    cover/                动态封面
    player/               音乐播放器
    sync/                 外部数据规范化逻辑
  layouts/                页面布局
  pages/                  Astro 路由
  styles/                 全局样式和设计变量
public/
  audio/                  MP3 文件
  images/                 文章和收藏图片
scripts/
  sync-content.mjs        同步收藏数据
  publish.mjs             校验、构建、提交和推送
```

首页内容区采用按时间排序的个人动态流，将碎碎念、长文章发布、音乐收藏、画作收藏和动画进度放在同一时间线上。各类内容同时保留独立归档页：

```text
/notes
/articles
/collection/music
/collection/art
/collection/anime
```

## 本地写作流程

Obsidian 和 Typora 都直接编辑 Markdown，不需要经过专有格式再导出。将 `src/content` 作为 Obsidian Vault，或直接用 Typora 打开文章文件即可。文章模板由项目保存，至少包含：

```yaml
---
title: ""
date: 2026-09-18
type: note
tags: []
draft: true
summary: ""
---
```

本地流程分为两个明确动作：

1. `npm run dev`：启动本地预览；编辑器保存后由 Astro 热更新。
2. `npm run publish -- "可选说明"`：执行同步、内容校验、类型检查和生产构建；全部成功后，只暂存内容、收藏缓存和媒体目录，生成提交并推送当前分支。

发布脚本应满足以下约束：

- 构建失败、同步结果格式错误或 Git 不在预期分支时停止发布。
- 不使用 `git add .`，避免把实验代码和无关文件带入内容提交。
- 没有内容变化时不创建空提交。
- 默认提交信息使用当天日期和变更文章标题；命令行说明可覆盖默认信息。
- 推送失败时保留本地提交并明确报错，不回滚用户文件。

“自动提交并推送”指一次显式的发布命令或编辑器快捷键，不监听每次保存。这样仍然是一键发布，同时避免半成品文章形成大量提交。后续可以通过 Obsidian 命令插件或系统快捷方式调用同一条命令，但发布逻辑只维护一份。

## 收藏与同步

### 音乐

音乐来源为本地 MP3，不再接入网易云或其他音乐 API。每首歌由一个受版本控制的元数据记录描述，例如标题、艺术家、封面、文件路径、收藏日期和简短备注。MP3 是否直接进入 Git，需要在迁移时根据仓库体积和 EdgeOne 单文件限制决定；文件较多时改用对象存储，数据模型不变。

### 动画

Bangumi 是动画进度的自动同步来源。同步脚本在本地发布前和 EdgeOne 构建时调用官方 API，将远端字段转换为站内稳定格式后写入 `src/data/generated/anime.json`。

- Token 只通过本地 `.env` 和 EdgeOne 环境变量提供。
- 生成文件不保存 Token 或原始响应中的无关用户信息。
- API 失败时保留上一次成功缓存，不让博客构建失败。
- 请求频率保持在发布/定时同步级别，不由每位访客触发。

### 画作

画作收藏同样采用“同步适配器 -> 统一数据 -> 本地缓存”的结构，但不把非官方 Pixiv 私有 API 作为稳定架构依赖。当前约束如下：

- 只有存在合规、稳定的授权数据源时才启用全自动同步。
- Pixiv 适配器必须与站点构建解耦；失效不能影响文章和其他收藏。
- 缓存只保留展示需要的作品 ID、标题、作者、原始链接、收藏日期和获准展示的缩略图信息。
- 不绕过访问控制，不抓取或重新托管无权分发的原图。

画作数据源是目前唯一未锁定的外部实现项。确定来源前，可以先建立统一数据结构和导入接口，但不承诺 Pixiv 收藏能够长期无人值守同步。

## 构建与部署

目标流水线：

```text
本地编辑 Markdown
  -> npm run publish
  -> 同步外部收藏并校验
  -> Astro 生产构建
  -> Git 提交和推送
  -> EdgeOne 从 Git 构建
  -> 发布静态站点
```

EdgeOne 构建也必须执行校验和生产构建，但不应依赖只有开发电脑才存在的文件。Bangumi Token 等密钥由 EdgeOne 环境变量提供。

第一阶段使用 Astro 静态生成，不依赖 ISR。动态封面和播放器在浏览器运行，文章与收藏页面在构建时生成。图片预处理由项目脚本完成，不把部署正确性绑定到平台特有的图片组件。

## Supabase 使用条件

当前架构不需要 Supabase。仅在出现以下明确需求时重新评估：

- 从多台设备写入尚未进入 Git 的私有草稿；
- 需要浏览器管理后台；
- 需要保存无法通过构建缓存解决的同步状态；
- 增加登录后的私人功能。

届时 Supabase 只承担上述新增能力，不迁移已经适合由 Markdown 和 Git 管理的正文内容。

## 实施顺序

1. 保存当前动态封面和播放器行为基线，整理原型与源素材。
2. 初始化 Astro 5 + TypeScript，并迁移封面和播放器。
3. 建立内容集合、模板、碎碎念流和长文章页面。
4. 实现本地预览、内容校验和一键发布脚本。
5. 接入 Bangumi 自动同步和失败缓存。
6. 建立本地 MP3 收藏模型与播放器歌单。
7. 确认合规的画作数据源后实现对应同步适配器。
8. 配置 EdgeOne 构建、环境变量和正式域名。

每一步完成后都必须通过生产构建；涉及页面的步骤还需分别检查桌面端、移动端和减少动态效果模式。
